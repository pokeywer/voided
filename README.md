# VoidedX

VoidedX is a static website with Vercel serverless API routes. Deploy the repository root with the project's existing Firebase and Vercel configuration. API paths dispatch through one catch-all Vercel function to stay within Vercel Hobby's function-count limit; the underscore-prefixed files in `api/` are internal handlers and helpers, not separate routes.

## Admin setup

The admin page at `/admin.html` uses the `/api/admin-auth` route. Configure these Vercel environment variables before deployment:

- `FIREBASE_SERVICE_ACCOUNT`: the Firebase service-account JSON used by the server-side API routes.
- `ADMIN_USERNAME`: the admin sign-in name.
- `ADMIN_PASSWORD`: a private password of at least 12 bytes.
- `ADMIN_SESSION_SECRET`: a separate random secret of at least 32 bytes. Changing it signs out existing admin sessions.

Admin sessions use signed, HTTP-only, same-site cookies and expire after eight hours. Sign-in is limited to five failed attempts per network address in a 15-minute window. The client-side Firebase security rules are not part of this archive; review the rules configured in Firebase separately, especially for direct vault and key-manager writes.

The authenticated Admin dashboard includes a private vault source manager. It lists vault metadata, loads readable source only when a vault is selected, and can update its title, source, obfuscation settings, and execution copy. Admin edits are protected by the same-origin check and session cookie, and update only the chosen vault's script fields while preserving owner keys and execution counts. Saving there changes the live vault used by that vault's loader.

## Discord bot and control panel

The Discord Control page is available at `/discord.html` and is linked from the authenticated Admin dashboard. It uses the existing admin session and stores channel IDs, editable channel panel text, and IDs of bot-posted panels in Firestore. The Discord bot token is never returned to the browser or stored in Firestore.

This integration uses Discord HTTP interactions, so it does not need a continuously running bot process. Its guild commands are registered only for application `1563789940452622397` in guild `1563443676313559100`; the interaction handler independently rejects interactions from all other guilds and validates Discord's Ed25519 request signature. The configured channels are Rules, Notices, Features, Top-Globals, Chat, Suggestions, Site, Blacklist, Bypass, and Commands. `/help`, `/panel`, `/scripts`, and `/verify` work throughout the allowed guild. Channel commands are limited to their mapped channel after a channel ID is entered in Discord Control. The `/bypass` response only directs users to legitimate access help; it does not bypass a protection or verification check.

To connect the bot after deployment:

1. In the Vercel project settings, add `BOT_TOKEN` as a private environment variable and redeploy. The server also accepts the older name `DISCORD_BOT_TOKEN`. Never put this token in HTML, client JavaScript, a commit, or a chat message.
2. In the Discord Developer Portal, install the application into the specified server with the `bot` and `applications.commands` scopes. Grant the bot only the permissions it needs; publishing channel panels requires Send Messages and Embed Links in those channels.
3. In the app's General Information settings, set the Interactions Endpoint URL to `https://voidedx.vercel.app/api/discord-interactions`. The app's public key is already configured in the server handler. Discord validates the endpoint with a signed PING request.
4. Sign into `/admin.html`, open Discord Control, enable Developer Mode in Discord, right-click each text channel and choose Copy Channel ID, then enter the IDs and save.
5. Click Register commands, then Publish channel panels. Publishing updates the bot's prior panel message when possible; otherwise it sends a new one.

`/verify vault_id:<id>` opens the existing VoidedX vault access page. It does not link a Discord account to a website/Firebase account or assign Discord roles. Those require an additional OAuth and role-management integration; website key-page verification does not by itself prove Discord membership.

### Obfuscator page, void tokens, and the Discord link

Every account gets **8 void tokens per day**. A token is spent after a copy is generated, the daily counter resets at 00:00 UTC and does not bank, and the page reports the remaining count, any bonus balance, and the reset time. Admins add or clear bonus tokens for a Discord user ID or a VoidedX account ID in Admin → Void tokens; bonus tokens are spent after the daily ones and never expire. The ledger lives in `obfuscationTokens/{subject}` with `discord:<userId>` and `web:<firebaseUid>` subjects; spends run in a Firestore transaction, and an exhausted allowance returns 429 with the reset time instead of silently failing.

The website allowance cannot be refreshed by signing out and back in. The server derives the subject from the verified ID token, never from anything the browser sends, and `obfuscationTokenAliases/{sha256(email)}` points every account that proves the same verified email at one ledger. A new sign-in session keeps the same `web:<firebaseUid>` record; a different provider (email/password, Google, Discord) with the same verified email is folded onto that record with its usage and grants merged, so it never receives a fresh batch. Unverified password addresses and unlinked accounts stay keyed by UID. The Discord link spends the Discord user's own `discord:<userId>` balance, which is separate from website accounts.

The public page needs no link, but it now requires a real account. `site-auth.js` gates every visitor page (`/`, `/obfuscation`, `/scripts`, `/keysystem`, `/panel`, `/staff`, `/key`, `/leaderboard`, `/vault`) behind an email/password, Google, or Discord sign-in before the page unlocks; admin and Discord panels keep their existing admin login. The page sends the Firebase ID token to `GET`/`POST /api/obfuscation-tokens`, which rejects anonymous sessions, and spends that account's own balance. If the browser still holds a leftover anonymous session, signing in calls `POST /api/claim-guest-vaults`; the server verifies both ID tokens and moves every vault owned by the guest UID onto the signed-in account, so they appear immediately in the editor and Creator Panel. Linking instead of switching (email sign-up, Google, or Discord on the guest session) keeps the same UID, so the vaults never need moving. The gate also has a forgot-password view that sends a Firebase reset email, and it pins auth to `browserLocalPersistence` so a deploy, refresh, or browser restart keeps the session instead of asking for the password again. Both the page and the script editor expose the same build options — strength, armor layers (1-6 or the strength default), junk preamble (off/normal/heavy), gibberish comments, messy or compact layout, tamper check, extra string splitting — plus auto-download and copy on the page. The page presents those options as segmented controls and switches rather than native selects, keeps the last choices in `localStorage['voidedx-obfuscator-settings']` until Reset is pressed, and shows a live source readout (characters, lines, bytes) next to the editor. After a build it reports the result size, character count, line count, build time, and the settings used for that copy. Source tools include Choose file, Paste from clipboard, Clear with a confirmation dialog, and Ctrl/Cmd+Enter to run. The token card renders one segment per daily credit, and `i18n.js` ships on the page so the English/Português do Brasil switcher in the top bar also translates the obfuscator.

`/obfuscate` still creates a private link. The command takes an optional `.lua`/`.txt` attachment or pasted `code` plus an optional `level`, and replies with an ephemeral embed containing `https://voidedx.vercel.app/obfuscation?vx=<token>` (the `/obfuscationvx=<token>` rewrite also works). Opening the link preloads the uploaded source or pasted code. Sessions live in `obfuscationSessions/{token}` and `obfuscationSessionOwners/{discordUserId}`. Link tokens are 192-bit random `base64url` values and expire after 7 days; a user has one active link at a time, so running `/obfuscate` again refreshes that link's source and reuses the token while it is still valid, because the count comes from the shared daily ledger rather than per-link credits. Expired sessions are deleted when read, and `GET`/`POST /api/obfuscation-session` return 404/410/403 with a message instead of a stack trace.

The page downloads the generated `.lua` and can also save the generated copy to a new vault. Saving uses the signed-in Firebase account and the same Firestore schema as the Creator Panel: `encodeVaultSource` for the source, `encodeObfuscatedCode` for the execution copy, `obfuscationEnabled: true`, the chosen `armorLayerCount`, `junkPreambleMode`, `junkCommentsEnabled`, and `armorLayout`, and the standard 10-hour auto-delete. Vault saving is subject to the same 5-vault and Firestore document-size limits, and the vault belongs to that account, so it shows up in the editor and Creator Panel on any device. No Discord account is linked, so a leaked link can be used by anyone who has it until it expires or that user's tokens run out.

## Get-Key link steps

The public Get-Key page (`/key.html?id=...`) can require a completed link step before it issues a key. Owners choose the provider in Key System → Public Key → Link step:

- **No link step** issues a key after the safety wait.
- **Custom link** opens any HTTPS reward page. Set the Return template (`...&ticket={vx_ticket}`) as that page's destination, or use the ticket in your own flow; the ticket is 20 minutes and one-use.
- **Linkvertise** requires Anti-Bypass on the link. Set the link's destination to your Get-Key page, paste the 64-character Anti-Bypass token into the panel, and the server checks the returned `hash` against `publisher.linkvertise.com/api/v1/anti_bypassing` before issuing a key.
- **Work.ink** needs no secret. Set the link's destination to your Get-Key page; Work.ink appends `?hash=` when the step finishes and the server checks it against `work.ink/_api/v2/token/isValid/<hash>` with `deleteToken=1`.
- **LootLabs** uses a postback. Copy the generated postback URL into LootLabs → Advanced and leave the locker link as the destination; each visitor's ticket is attached as `puid`, LootLabs reports it back as `click_id`, and the key page unlocks on its own.

Provider-host checks, the tracker token, the completion hash, and the wait timer are all enforced server-side in `api/_route-keypage.js`; the browser only renders what the routes return. A completion hash is claimed once (`gatewayCompletions`), so a captured return URL cannot mint a second key, and a claim whose provider or link changed after it started is rejected.

Linkvertise tokens are stored encrypted in `gatewayCredentials/{vaultId}`. Set `GATEWAY_ENCRYPTION_KEY` in Vercel to a base64-encoded 32-byte key (generate one with `openssl rand -base64 32`) before saving a Linkvertise token; `LINKVERTISE_ENCRYPTION_KEY` is still accepted as a fallback name. LootLabs postback secrets are generated per vault and reused while the provider stays LootLabs; switching away and back rotates the secret, so paste the new URL into LootLabs again. The postback URL contains a secret — share it only with LootLabs. `LINKVERTISE_API_BASE` and `WORKINK_API_BASE` exist only to point the verifiers at a mock server during testing.

Verification calls the live provider API, so a provider outage returns a clear "could not be reached" message instead of issuing a key, and the flow never accepts a bare return URL as proof.

## Loader and key protection

The copied loader keeps the stable `loadstring(game:HttpGet(".../api/raw?id=..."))()` form and contains no token query parameter or format flag. Executor requests to `/api/raw` receive the bootstrap by default; normal browser requests are redirected to the vault page. Each `/api/raw` fetch mints a new signed 10-second loader token and encrypts the returned bootstrap with a token-derived seed; that bootstrap rechecks the token when run. A copied bootstrap body expires, while the token-free outer URL can fetch a new bootstrap whenever the vault remains available. Owners can increment the vault version to invalidate already-issued bootstrap bodies, pause the vault to block new launches, or revoke a key to block future keyed access. Each successful `/api/verify` call also issues a cryptographically random, one-use delivery ticket; it expires after the vault's configured 20, 30, 45, or 60 seconds (45 by default) and `/api/payload` consumes it once while rechecking the vault, key, player binding, ban, IP-lock state, and pause status. The payload route only answers with the shielded form: the execution copy is re-derived server-side, encrypted into shuffled parts with the ticket's per-session seed, and returned with a checksum tag over the ciphertext, while a ticket that carries no shield is refused instead of falling back to a plaintext body. Keyed verification limits can be set to 5, 10, 20, 30, or 50 checks per network in 15 minutes (30 by default); the counter includes successful checks. Pausing does not stop a script that has already been downloaded and is running. Newly generated keys use 16 cryptographically random characters; existing keys continue to work. Loader tokens minted by `/api/raw` are bound to the requesting network by default; set `LOADER_TOKEN_IP_BIND=0` if an executor's HTTP egress IP changes between the bootstrap fetch and its token-check gate. `LOADER_TOKEN_SECRET` may be set to a random secret of at least 32 bytes; if unset, signing and seed derivation use `ADMIN_SESSION_SECRET`, then `FIREBASE_SERVICE_ACCOUNT`.

Generated loaders no longer ship the inner loader as plaintext inside the response. The bootstrap is encrypted with a token-derived Xorshift32 keystream, and the seed is released only by a separate `/api/raw?...&format=token-check` gate request after the token, network binding, vault version, key, and pause checks pass. A captured bootstrap body therefore cannot be decrypted offline without a live, valid gate request. The bootstrap opens with an ASCII `VOIDEDX LOADER` banner, and the gate URL — which carries the live token — is stored as ciphertext under a per-build key instead of a readable literal, so a dumped body no longer shows the endpoint or the token. Every generated local name is randomized per build, from one of three name styles. Each build also fires two to four decoy gate requests with fabricated loader tokens built in the same shape as issued ones (base64url JSON payload with version, vault, key hash, vault version, expiry, nonce and binding, plus a random signature), requested exactly once each in a randomized probe order. Where the executor provides `task.spawn`, every candidate is launched at once and the loader resumes as soon as one reply parses, so a yielding `HttpGet` overlaps all of them, while a blocking `HttpGet` simply runs them in order and the unprobed ones are still fired once; either way a captured request log shows every gate URL exactly once and no URL stands out. The gate now answers from the signed ticket alone instead of reading Firestore, so a log shows several identical-looking `format=token-check` fetches that cannot point at the live credential, replaying the wrong one only burns a rejection, and a launch no longer waits on a database round trip per candidate. A reply is accepted only in the exact `vx1|<8 hex>|<16 hex>` shape the gate issues, so a body that merely starts with `vx1|` cannot steer the seed. The decrypted plaintext is prefixed with a per-build `--[[vb:...]]` marker, and the check runs on the first part before the remaining parts are decoded, so a body opened with a stale or fabricated seed fails immediately and reports an expired loader instead of compiling garbage. Before the gate request and again before decrypting, the bootstrap compares the runtime against references it captured at start (`string.byte`/`char`/`sub`/`gsub`/`match`, `table.concat`, `pcall`, `error`, `type`, `math.floor`, `loadstring`/`load`, `string.dump`, `game.HttpGet`, and, when present, `bit32`, `getgenv`, `getfenv`, `setfenv`), and it also compares the `loadstring`/`load` entries seen through `getfenv(0)` and `getgenv()` against the captured ones, so a wrapper installed in only one channel is still caught. It probes `string.dump` against both compile entries: a native `load` rejects a dumped Lua function while a Lua-level wrapper accepts it, which exposes `hookfunction(loadstring, ...)` shims that forward to the original. It refuses to continue when one of these has been swapped, and it installs a `debug.sethook` function-count watchdog that rechecks the same references (and that the hook is still its own) for the first ~16M instructions or 10 seconds; a foreign hook, a removed hook, or a re-swapped builtin disarms it and aborts. The watchdog marks itself in `getgenv()._vxwd` so the armor recognizes it as expected. Both denials exit with `Voided: Doing this is not allowed.`, so a naive `env`-log, `hookfunction`, or dump-shim fails instead of printing the loader. Compilation prefers the native `load` when `loadstring` has been replaced and, when the executor supports a function reader, feeds the decoded source to the compiler in 4096-byte chunks instead of one string, so an argument logger placed on the compile entry sees fragments rather than the loader text. The gate and every delivery request are logged against a per-session trace. Decoding itself is byte-oriented rather than character-oriented: the alphabet is keyed by byte value, four base64 characters leave in one `string.byte` call, four decoded bytes leave in one `string.char` call, and the keystream advances once per 32-bit word, which cuts local decode time by roughly a third on large bodies without changing the wire format. The plaintext that gets sealed is scrambled first (`api/_loaderObfuscator.js`): local and parameter names are renamed, string literals are moved into a per-run encoded table decoded in memory, and the body is emitted minified, so a chunk dumped after decryption reads like machine output instead of a documented loader. The single readable line is the `-- VoidedX Loader` credit comment.

GUI mode (`requireKey` with `guiMode`) keeps the key out of the URL entirely: the loader draws an in-game key card with the vault's name, title, subtitle, button label, accent colors, and one of 15 background animations, verifies the key through `/api/verify`, saves it locally when the executor supports `writefile`, re-checks it on the next run, and shows a small key-status card with a draining expiry timer before the payload runs. Removed vaults render a matching "VAULT OFFLINE" warning card instead of failing silently.

Payload delivery is split between two requests and a one-use ticket. `/api/verify` returns a delivery ticket, a per-session key, and a 16-hex trace; the ticket is stored server-side with the requester's address hash, client signature hash, player ID, place ID, and issue time, and `/api/payload` accepts it once, only from that same connection, then deletes it. The payload response carries the encrypted parts in order plus a CRC32 of the ciphertext; the plaintext checksum stays on the server, so a captured response cannot be used to confirm a decode. The loader accumulates the ciphertext checksum while it decodes the parts, compares it before decrypting, and checks the `--[[vx:TRACE]]` watermark after, so the payload is read once before decryption and a session key only opens the copy it was issued with. Capturing either response alone does not yield the script. The runtime compares `game.HttpGet`, `loadstring`/`load`, `HttpService.JSONDecode`, `string.char`/`byte`/`sub`, `table.concat`, `pcall`, `rawequal`, and `debug.info` against references captured at start; it also checks `print`, `tostring`/`tonumber`/`type`/`next`/`ipairs`/`setmetatable`/`rawset`, `math.floor`, `string.format`/`rep`/`gsub`/`match`, `game.GetService`, `HttpService.UrlEncode`, and `task.wait`/`spawn`, plus `string.dump`, `error`, `debug.sethook`/`gethook`, and `getfenv`/`setfenv` where the executor provides them. It also cross-checks the bootstrap's `getgenv()._vxwd` marker against `debug.gethook`, so a hook installed after the watchdog expires is recorded as `hook_installed`; those late-swap and foreign-hook flags are recorded and visible on the admin side but are not blocking on their own, so an executor or another script that touches its own globals mid-session is not locked out. Compilation switches to whichever of `loadstring`/`load` is still native and, when supported, reads the decoded source through a 4096-byte reader so an argument logger on the compile entry receives fragments; if reader-mode compilation returns nothing, the loader retries the full string and then the other compile entry before reporting a failure. The integrity failure path now reports the actual reason (`payload_crc_mismatch`, `watermark_missing`, or `payload_shape_invalid`) instead of an empty flag list. Before the payload is requested it publishes a decoy `getgenv().VoidedX` table: its `unlock`, `bypass`, `signature`, `extract`, `payload`, `key`, `token`, and `session` helpers, plus any unknown-field read, report `honeypot_triggered`, which is a blocking flag. Swapped functions are reported to `/api/integrity`; high-confidence flags mark the one-use ticket blocked, so `/api/payload` refuses delivery, and every report is stored with the trace, vault, player, IP, and user agent. Each payload begins with a `--[[vx:TRACE]]` watermark, and `loaderDeliveries/{trace}` maps it to the vault, player, key issue, and delivery IP for leak forensics. The optional fast-load plaintext cache is not used by shielded loaders because an on-disk plaintext copy defeats the protection.

This raises the cost of casual `HttpGet`/`loadstring` dumping and makes leaks attributable, but it is not DRM. A caller who runs the whole delivery flow still receives every part and the key that opens them, so the ticket, the binding and the checksum change the cost and the blast radius, not the outcome. Code that a client can execute can be captured by a runtime that is already compromised, for example a hook installed before the loader starts, an executor that patches `game:HttpGet`, or a modified loader that strips the checks. Keep secrets and private API credentials out of client scripts.

Each generated inner loader starts with a `-- VoidedX Loader [https://voidedx.vercel.app]` comment and prints `[VoidedX] VoidedX Protection - protect your scripts at https://voidedx.vercel.app`. The **Instant run** option in Vault Protection (on by default) then starts the execution copy immediately with no other console lines. With Instant run off, the loader also prints an ASCII progress bar in Roblox's F9 Developer Console while the execution copy is downloaded, checked, and compiled, for example `[VoidedX] [=======-------]  50%  Downloading payload`. The credit line appears only after the gate decrypts the inner loader; the `/api/raw` response itself stays a banner, ciphertext, decoder, and the instrumentation guard described above. The percentage is an estimate because `game:HttpGet` does not expose byte-level download progress; it stays below 100% until the response arrives and reaches 100% when the script is ready to start.

## Vault protection and obfuscation

Vault Protection runs the bundled engine in the browser. The prebuilt engine under `prometheus-engine/` is started in a module worker, compiles the script to its VM bytecode, and returns the protected copy; the page patches a known executor crash by rewriting bare `#` length operators to a safe helper. That copy is then repacked in the VoidedX armor (`lua-voidedx-armor.js`): the engine watermark is rebuilt from split literals, internal helper names are renamed, decoy functions and opaque guards are added, and the result is LZSS-compressed, masked in passes, split into shuffled segments with shuffled keys, and wrapped in a randomized loader with its own adler32/weighted-sum integrity checks, builtin-identity guard, marker-aware debug-hook guard, and Roblox gate. The container is polymorphic: each build picks its own byte mixer (add, subtract, or affine with a modular inverse), its own 32-bit state-chain constants and keystream shift, its own LZSS token split point, minimum match length, offset byte order and offset bias, its own buffer sizes, its own identifier style, and its own segment permutation, which is rebuilt at runtime from a seed. The keystream also mixes the previous ciphertext byte and the absolute stream position, so a segment cannot be decoded on its own, and two builds of the same script share no constant and no decode shape. The delivered script therefore does not carry the engine's recognizable layout, and tampering with the payload fails before `loadstring` runs. The fork maps Fast, Low and Medium to Medium and High and Absolute to Strong; no level uses the readable Weak preset. Every level uses exactly one Prometheus VM layer; a second Vmify pass over the first VM's own bytecode corrupts a fraction of programs in every interpreter we test, so High and Absolute take their extra weight from the Strong preset and the heavier armor levels instead. Extra depth comes from nesting independent VoidedX containers rather than stacking VMs: every container is the same proven decode-then-load path, so a layer only re-wraps the previous copy. Fast nests one container, Low two, Medium four, High five, and Absolute six; each layer re-encodes the previous one at roughly 1.35x, so nesting stops before a single layer exceeds 420 KiB and before the total passes 3 MiB, keeping large vaults storable. Low, Medium, High, and Absolute each use a progressively heavier armor pass (Medium applies five mask passes over eighteen segments, High and Absolute add a second opaque guard). Low and above also inject VoidedX decoy routines, a seed-bound VoidedX watermark, and the Sigil Cipher string step into the VM program, and each build renames generated identifiers with a seed-derived prefix. The Sigil Cipher replaces the stock string encryption: its keystream is integer-only, so encoder and decoder stay bit-identical on LuaJIT, Lua 5.4 and Luau, where the stock cipher's fractional `2^x` keystream drifted and corrupted a share of strings. Absolute also enables tamper checking and extra string splitting, and the Tamper check and More string splitting controls pass those options through for other strengths. Auto selects High up to 16 KiB of UTF-8 source and Low above that, and owners can override the selection. Stronger settings take longer and produce larger output; Absolute is the slowest and is the most likely to break a script. Keep a readable backup and test the generated copy in a private place before replacing a live vault. Obfuscation errors stop saving before Firestore is updated, leaving the prior vault unchanged. The `HttpService:JSONDecode(response)` call in the loader parses the server's JSON envelope; `res.json()` escapes the delivered source correctly. It is not a way to hide client code: any code delivered to a client for execution can be captured at runtime.

Based on Prometheus by Elias Oelschner, https://github.com/prometheus-lua/Prometheus. The fork's license and attribution terms are in `LICENSE-PROMETHEUS.txt`.

Obfuscation profile 30 gives the container two virtual machines instead of one, and makes the names unreadable. The step program is now built in one of two shapes per build: the linear dispatcher (read in order, relabelled while it runs) or a chained one, where every step stores the byte index of its successor and the pairs are scattered through the program, so the order in the file is not the order that executes and the entry point is itself a per-build number. Half of all builds get each shape, and a chained program costs 12 extra bytes, not another engine, so sizes did not move. Identifier generation gained two confusable styles on top of the existing four: names built only from characters that collapse together in editors (`l`/`I`/`1`, `O`/`0`/`o`, `S`/`5`, `Z`/`2`, `B`/`8`, `G`/`6`, `q`/`9`), which is what `l0li0lil0ili0` looks like in a dump, and it applies to the loader names as well as the filler. Container depth stays at six layers by default: eight layers were measured at 460-590 KiB for a ten-line script, which is the heaviness to avoid. Validated across 30 single-layer builds (15 chained, 15 linear, all producing the source script's output), the 10-variant level matrix in Lua 5.4 and LuaU, 8 real Prometheus outputs, and the full delivery harness.

The inner loader obfuscator is now scope-aware. It previously collected every declared name into one flat table and renamed every occurrence of that spelling, so a local that shadowed an outer variable of the same name, or a global with the same name as some inner local, was merged with it: one silent behaviour change per collision, and the loader is the file that carries the gate URL and the decoys. It now walks the token stream with a block-scoped binding stack (locals, loop variables, parameters, `local function`, nested blocks, `repeat`/`until`, `elseif`/`else` chains and method definitions), resolves every reference to the innermost visible binding, leaves globals and table keys and `.`/`:` fields alone, and defers a `local x = ...` binding until the initializer expression has actually ended. Verified against a 17-case corpus that exercises shadowing, multi-value returns, closures over loop variables, generic-for shadowing, same-named nested parameters, `while`/`break`/`repeat`, and method chains using `self`: original and obfuscated output match line for line, and the full delivery harness stays green. No profile number changed: this affects the loader that is generated per fetch, not the protected copy stored with a vault.

Obfuscation profile 29 takes the sample-obfuscator shapes that actually work and folds them into both stages. The loader's dispatcher now rewrites itself while it runs: every few steps it swaps the keys of the next two steps in the handler table and exchanges the matching program bytes, so the mapping a live dump sees at step k is not the mapping at step k+1, and no static read of the table matches what executes. A time budget measured with `os.clock` refuses a run that took far longer than a real start, which is what single-stepping a trace looks like. The same two devices and interleaved state-machine filler are in the delivery bootstrap, which also mints a per-fetch session id and, only where the executor exposes `writefile`/`readfile`/`isfile`, drops a small marker file holding nothing but that id, so a file on disk can never be turned into a dump. Keys and sessions stay where they already were: the ticket, the IP-bound token and the per-session seed do the binding, and the loader refuses any interpreter that is not a live Roblox client before it makes a request.

Obfuscation profile 28 closes the hook-detection path that did not depend on `debug`. Until now a wrapped `load`/`loadstring` was caught by asking `debug.info`/`getinfo` whether the entry was still native, which an attacker who also replaces `debug.info` can defeat. The loader now calibrates on a known builtin first: on a host whose `string.dump` rejects its own C functions (`pcall(string.dump, string.byte)` fails), a dump that succeeds proves the entry is a Lua closure, so a `hookfunction` wrapper on the compile entry, `pcall`, `error`, `table.concat`, `type` or `string.char` is refused without consulting `debug` at all. Where `string.dump` accepts anything the probe stays silent instead of producing a false positive. Both the armor loader and the delivery bootstrap carry it, so a hooked load is refused in either stage. Cost is a handful of `pcall` calls at start, which is why the check runs where it matters rather than per byte.

Obfuscation profile 27 turns the loader's own runtime into a program. The steps that were emitted as statements -- the integrity gate, decode, compile-entry probe, inflate, chunk compile, chunk-name tripwire, the post-compile re-check and the hook restore -- are now closures stored in a shuffled table under per-build opcode numbers, and the order they run in is a sealed byte program that is checksummed before the first step executes; two no-op steps are mixed in at random. Nothing in the file says which step follows which, and patching the program refuses to run instead of skipping a check. The same construction is applied to every nested container, so a copy at Absolute runs the program inside each of its six layers, and the filler blocks are interleaved between the steps rather than only sitting in front of the file. Size stayed where it was: about 36-44 KiB at Fast and 217-260 KiB at Absolute for a small script, well under a megabyte, because the program replaced statements instead of adding another engine. The single Prometheus VM layer stays single: stacking Vmify corrupts real scripts, so depth comes from these independent VoidedX containers.

Obfuscation profile 26 is the anti-tamper pass. The loader now refuses three more kinds of interference at start: a `load`/`loadstring` replacement that answers a nil chunk (the real entry rejects it), and a `string.char` replacement that casts out-of-range values instead of failing, in addition to the existing native-identity checks on `pcall`, `error`, `rawequal`, the string and table primitives, `string.dump`, `debug.info` and the hook entry points, the two-channel environment consensus, the watch-only hook requirement and the per-build canary byte. The confusing filler is now interleaved inside the loader instead of only sitting in front of it: after the block that defines each helper, a build may wedge in one to three state or register machines, so the decode pipeline is never a run of neighbouring definitions. Volume was cut back on purpose, because padding is not strength: normal builds carry 12-21 filler blocks and heavy builds 26-39, scaled by strength, and the state machines are what make the file read as noise. The protection itself is unchanged and still single-VM: one Prometheus layer, the sealed VoidedX containers around it, and a delivery flow that only releases a payload against a live ticket. None of this stops a determined reader who controls the interpreter; what it does is make casual dumping, hand-editing of the guards, and textual/AI-assisted reading measurably more expensive.

Obfuscation profile 25 makes the delivered copy physically large and noisy. The junk preamble now draws from two generators besides the one-line shapes: a numeric state machine (a state id, an accumulator, four to seven states, a branch per state with thresholds that are sometimes unreachable, so the flow cannot be folded to a single value) and a four-register byte machine driven by an embedded instruction list (xor, add, multiply-add, and). Each block is a multi-line `do ... end` that declares only its own locals and clears them before it ends, so it cannot change the script; a build now carries dozens of them, more at higher strength and roughly twice as many on the heavy junk setting. Measured on a small sample, the junk adds about 8-28 KiB at the normal setting and 24-61 KiB at heavy across Fast to Absolute, on top of the previous size, and a heavy Absolute copy of a three-line script lands around 1,270 lines. This raises the reading cost and the cost of a naive diff, but it is padding: the protection still comes from the VM, the sealed containers and the delivery gate, not from volume. Profile 25 also fixes the loader block order so the Roblox check can only use the message helper after that helper is defined.

Obfuscation profile 24 reworks the delivery bootstrap and the armor loader's layout. The bootstrap is no longer a flat script: every step is a generated handler, the handlers sit in a shuffled table under per-build opcode numbers, and the run order is a sealed opcode program that is checksummed before it executes, so the file no longer shows the probe-decrypt-compile sequence as readable code. Every sealed blob (payload parts, gate URLs, the opcode program) now passes through a per-build 256-byte substitution box after the keystream, and the inverse box is rebuilt at runtime from a sealed permutation. Part keys chain: each key mixes the checksum of the previous decoded part, so the parts only open in order and one captured part decrypts to noise, and a tail marker rejects a truncated body in addition to the head marker rejecting a wrong seed. The bootstrap carries no explanatory comments; only the VoidedX banner and the `-- VoidedX Loader` credit remain. The loader layout inside the armor is drawn per build as well: helper blocks are emitted in a dependency-safe shuffled order, loops are drawn as `while` or numeric `for`, and the loader cross-checks the same builtin through `getfenv(0)` and `getgenv()` before it decodes anything, so a wrapper installed on one channel disagrees with the other and the run stops. It also rejects a compiled chunk whose `debug.info` source name is neither the name it asked for nor a host-provided value, and it checks a canary byte at a random offset of the compressed stream, which catches a patched length or checksum branch. The bootstrap is generated per request and never stored with a vault, so every existing vault serves the new bootstrap on its next fetch without being re-saved; the profile number only marks stored protected copies, which keep launching until the owner saves them again. Vaults saved before a profile bump do not need a migration to get the current loader: `/api/raw` builds the delivery bootstrap per request, so every vault serves the current one on its next fetch whatever its age. Only the stored execution copy is tied to the profile it was saved with. The admin panel's **Rebuild outdated copies** action walks every vault that is below the current profile, re-obfuscates its stored source at the strength and protection flags that vault already uses, and replaces the live copy; vaults already on the current profile are skipped, a single failure does not stop the run, and the run reports what it rebuilt and what it could not.

Obfuscation profile 23 is the full rework. Every strength now goes through the same pipeline, and the selector only changes the pipeline settings: Fast, Low and Medium use the Medium preset and High and Absolute use the Strong one, so the old readable Weak output, which a dumper recovers in a single pass, is unreachable from any selector including Auto. Armor defaults were raised across the board: segments 14/18/26/32/40, mask passes 3/4/6/7/9, LZSS depth 44/68/92/108/152, dead functions 3/4/5/6/7 and nested containers 2/3/5/6/6 for Fast, Low, Medium, High and Absolute. Each nested container wraps its body in one to three extra trampoline frames with fresh identifiers, carries at least two dead functions and a second opaque guard that is evaluated unconditionally instead of being an optional variant, and the outer loader re-runs its full integrity check plus a late opaque gate after the chunk is assembled and immediately before it is invoked. The runtime also checks that `string.dump` and `debug.info`/`getinfo` are native (`what == "C"`) next to the existing `load`, `pcall`, `error`, `rawequal` and string/table checks, so a hooked dump or info call is refused before the payload runs. Every level still uses exactly one Prometheus VM layer. Measured on a 2.2 KiB sample the delivered copy grows to about 92, 151, 300, 473 and 410 KiB for Fast, Low, Medium, High and Absolute (the Strong preset emits a different amount of inner bytecode per seed, so High and Absolute can land on either side of each other), and the gzip-base64 stored copy stays between 84 and 467 KiB, inside the 920 KiB document budget. All five levels were built through the real engine worker and validated end to end: every artifact passes `luac -p` and reproduces the source script's exact output in a Lua 5.4 host that stubs the Roblox and executor globals, including closures, metatables, varargs, method calls, string methods, coroutines and `pcall` error paths. This raises the cost of deobfuscation; it does not make a copy that runs under its own loader impossible to reach.

Obfuscation profile 22 raises the armor defaults and hardens the loader. Armor levels now nest Fast 1, Low 2, Medium 4, High 5 and Absolute 6 VoidedX containers with 8, 12, 18, 24 and 32 segments, 2, 3, 5, 6 and 7 mask passes, LZSS depth 28, 52, 72, 88 and 128 and 2, 3, 4, 5 and 6 dead functions, still behind exactly one Prometheus VM layer. Measured on a 13 KiB script the delivered copy grows to about 26, 43, 92, 143 and 221 KiB, roughly 1.5x the previous Medium, High and Absolute output; a 128 KiB input gains less because the nesting caps stop additional layers early. The extra weight also moves the vault size ceiling: a large source at High or Absolute can now exceed the ~920 KiB document estimate and is refused at save time with the existing "choose Fast or Medium" message, so Medium stays the practical choice for scripts around a hundred kilobytes. Expanded transforms are now on by default for every level above Fast instead of being opt-in, and the checkbox in the editor reflects that, so the lighter Fast profile only changes the engine's step set, never whether the script reaches the VM. The inner loader that the gate releases is hardened further: each build draws one of four identifier styles (`_0x` hex, two-syllable, base36, or single letter with a numeric suffix), every string literal is split by content hash across two byte-encoded tables that are stored in shuffled order and each decode with their own key and step, the tables are built inside a `do` block behind the always-true opaque predicate `(n*n+n)%2==0` with an unreachable branch that carries a decoy `token-check` URL and a decoy refusal, the body is broken into ragged lines at random, and a naive `string.match` on the dumped text finds a URL that is not the live one. The bootstrap is regenerated per fetch as before, and the per-fetch variation is now wider: three xorshift codecs with three distinct byte schedules, a shuffled base64 alphabet, one to three ciphertext parts with per-part keys, and the live gate URL shuffled among two to four sealed decoys that are probed in a randomized order, with the remaining decoys fired concurrently through `task.spawn` as noise. A captured response body is therefore built for one token and one layout, and the next refresh shares no alphabet, no codec, no part count and no probe order with it.

Obfuscation profile 20 marks the previous container. It changes no container shape; it fixes a miscompile that only appeared above High strength. The engine's number-expression step rebuilt large integer literals through modulo chains whose intermediates crossed 2^53, where IEEE-754 doubles stop representing every integer, so a copy evaluated in LuaU could rebuild a different value than the one the pipeline intended. One such value is used as a VM operand index, which silently flipped a branch and produced `attempt to concatenate nil with string` or a wrong result. Generated expressions are now capped at 2^40 and fall back to a plain literal above that, which is exact in both Lua 5.4 and LuaU. The same profile number is stamped on saves, so vaults written by earlier builds are flagged and rebuilt when saved again. Every delivered copy opens with an ASCII `VOIDEDX OBFUSCATION` banner and 16 to 29 inert `do ... end` junk blocks before the `-- VoidedX` marker; the junk only computes discardable literals, so it cannot change runtime behavior. The junk is regenerated per build and reads as noise: identifiers are drawn from the characters that collapse in monospace fonts (`l`/`I`/`1`, `O`/`0`/`o`, `S`/`5`, `Z`/`2`, `B`/`8`, `G`/`6`, `q`/`9`), the block shapes, numbers, escapes, and gibberish `--` comments are randomized, and no identifier repeats within a copy, so two builds of the same script share no preamble text either. The loader body is emitted unformatted on purpose: comments are stripped, statements are packed with minimal gaps, and line breaks land at random, so the file reads like raw VM output rather than a formatted script. Profile 17 makes the container polymorphic instead of fixed: a build chooses one of three reversible byte mixers, generates its own 32-bit chain multiplier, increment and content-mix weights, its own keystream shift, its own LZSS token split point, minimum match length, offset byte order, offset bias and buffer flush sizes, and its own identifier style, and every helper local in the loader is drawn from that fresh factory. The keystream advances with the previous ciphertext byte and the absolute offset, so decoding a single segment in isolation produces noise, and the segment permutation is generated at runtime from a seed rather than shipped as a readable table. Two builds of the same script therefore share no constant, no identifier and no decode shape, and a deobfuscator written for one file has to be rewritten for the next instead of replaying one reusable script. Every armor level still emits the debug-hook guard: it accepts a hook only when `getgenv()._vxwd` names it, so the bootstrap's own watchdog passes while a foreign hook or a stale marker is denied. Nested containers compile from a reader whose piece size is drawn per build (1-6 KiB, under the ~7000-result `table.unpack` cap that Luau and Lua 5.4 both enforce) and prefer whichever of `loadstring`/`load` is still native, so an instrumented compile entry sees fragments instead of plaintext. Profile 18 hardens the container against runtime capture, which is how a dumped copy is normally obtained. Every loader candidate is identity-checked before use: the loader looks at `loadstring`, `load`, `_G.loadstring`, `_G.load`, and the `load`/`loadstring` fields of `getfenv(0)`, `getgenv()` and `getrenv()`, then keeps the first candidate that `debug.info`/`debug.getinfo` still reports as a C function (`what == "C"`, or `"[C]"` on Luau). A `hookfunction(loadstring)` or `hookfunction(load)` proxy is a Lua closure, so it is rejected before any payload is compiled through it. The same native check covers the decode primitives (`pcall`, `error`, `rawequal`, `string.byte`, `string.char`, `string.sub`, `string.len`, `table.concat`, `table.unpack`, `math.floor`), because trapping `table.concat` or `string.char` captures a decoded chunk just as easily as trapping the loader; the check runs before decoding, again after decoding, and once more immediately before the compile call. Builds also no longer carry the engine's `eai_*` identifier family, which was the cheapest fingerprint for a reader that recognizes the engine: the dominant prefixed family is redrawn from the per-build name factory before compression (757-1354 occurrences per copy, zero after), with locals, upvalues and shadowing renamed consistently so runtime behavior is unchanged. The loader reports a missing executor primitive separately from a failed start, so an unsupported interpreter is distinguishable from a blocked copy. Profile 19 stops the chunk from ever existing as one string. The inflater is a pull iterator that keeps only the 64 KiB window and the token position and returns at most one 1-8 KiB piece per call; a literal run or a match copy that crosses a piece edge resumes exactly where it stopped, so where the loader accepts reader functions the plaintext exists only as the piece `load` is parsing, never as a full value a hook or `debug.getupvalue` can read. Roblox's `loadstring` compiles strings only, so there the loader gates on a working string compile alone, detects reader support separately, and concatenates the pieces immediately before compiling instead of refusing an interpreter that has no function chunks. The loader also clears the debug hook for the decode and compile and restores it immediately before the payload runs, so a dumper that satisfies the `getgenv()._vxwd` marker with its own hook sees nothing during the window where the copy is readable; the bootstrap watchdog covers the payload run as before. Tampering, integrity failure and a failed compile now share one message, and the old `vx_probe` string is gone, so the delivered file no longer documents which check fired. The engine's own anti-tamper probes dropped their readable tokens too: the failure message is empty, the `VoidedX` tag is built with `string.char`, and the concat probe compares numbers, so a dump no longer hands a reader the names of the checks it still has to satisfy. Low and above seal string literals with the integer-exact Sigil Cipher, the loader rejects a `pcall` that swallows errors, and the anti-tamper step probes only language-level invariants and tolerates one interpreter quirk. Each level keeps a single Prometheus VM layer and gains depth from nested VoidedX containers instead (profile 20 defaults: Fast 1, Low 2, Medium and High 3, Absolute 4, capped by payload size; profile 22 raises these as described above). Builds can override that count (1-6 layers), turn the junk preamble off or make it heavy, disable the gibberish comments, and choose the compact layout, which keeps statements on long packed lines; the defaults reproduce the profile 20 shape described above. Vaults saved with the profile 18 build, the profile 17 build, the profile 16 build, the profile 15 build, the profile 14 build, the earlier two-layer High/Absolute VM build, the profile 13 string step, the bytecode-VM engine (profile 10), unarmored copies (profile 11), or the earlier armor (profile 12) are flagged as older; open and save them again to regenerate the execution copy.

Source up to 128 KiB is stored as readable text in Firestore for owner audits; larger source is gzip-base64 compressed to preserve Firestore document space. Compression is not encryption. Older plain-text and gzip-base64 records remain supported, and loading a vault decodes compressed source into the editor. The execution copy is stored as plain text when it is ASCII and smaller than its gzip-base64 form, otherwise gzip-base64; the API decompresses base64 records before delivery. Browser previews accept source up to 4 MiB and generated output up to 32 MiB; saving source to a vault remains capped at 2 MiB. Outputs above 1 MiB are download-only so a very large string does not freeze the editor. Saved vault copies are limited to 4 MiB and each vault document is kept below an estimated 870 KiB; the combined source and execution copy can hit the document limit first. Large scripts can take several minutes to process or time out. Re-saving unchanged source with the same strength and protection settings reuses the last generated copy in that browser session.

The engine raises the cost of static reading and casual dumping, but it is not DRM. The VM bytecode keeps the Prometheus opcode set because the engine is a prebuilt binary with no source to renumber it; the armor hides the engine's watermark and layout, but someone who recognizes the bytecode format and has the Prometheus disassembler can still decode the program and read the VM instructions. A runtime that is already compromised can also capture the script after decoding, for example through a hook installed before the wrapper starts; the bootstrap's channel checks and watchdog cover a hook installed after the loader begins, not one already inside the executor. The profile 18 and 19 checks raise that cost rather than closing it: an executor that also hooks `debug.info`/`debug.getinfo`, or replaces the `debug` table before the loader reads it, can make a wrapper present as native; a line hook installed before the run still watches the loader's setup lines before the hook is cleared and the payload's own execution after it is restored; and a run inside a full-privilege environment can still be traced with `debug.getupvalue` or the script's behavior reimplemented from scratch without ever reading the file. The cheap paths - swapping `loadstring`, `load`, `table.concat` or `string.char` and printing whatever passes through - are rejected on a stock executor. Where the loader compiles strings only, as Roblox's does, the pieces are concatenated for the length of one compile call, so that window is narrow rather than closed. Keep private API credentials and secrets out of client scripts; the loader shield and server-side vault checks remain the enforcement boundary.
