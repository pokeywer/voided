# VoidedX

VoidedX is a static website with Vercel serverless API routes. Deploy the repository root with the project's existing Firebase and Vercel configuration. API paths dispatch through one catch-all Vercel function to stay within Vercel Hobby's function-count limit; the underscore-prefixed files in `api/` are internal handlers and helpers, not separate routes.

## Admin setup

The admin page at `/admin.html` uses the `/api/admin-auth` route. Configure these Vercel environment variables before deployment:

- `FIREBASE_SERVICE_ACCOUNT`: the Firebase service-account JSON used by the server-side API routes.
- `ADMIN_USERNAME`: the admin sign-in name.
- `ADMIN_PASSWORD`: a private password of at least 12 bytes.
- `ADMIN_SESSION_SECRET`: a separate random secret of at least 32 bytes. Changing it signs out existing admin sessions.

Admin sessions use signed, HTTP-only, same-site cookies and expire after eight hours. Sign-in is limited to five failed attempts per network address in a 15-minute window. The client-side Firebase security rules are not part of this archive; review the rules configured in Firebase separately, especially for direct vault and key-manager writes.

The authenticated Admin dashboard includes a private vault source manager. It lists vault metadata, loads readable source only when a vault is selected, and can update its title, source, obfuscation settings, and execution copy. Admin edits are protected by the same-origin check and session cookie, and update only the chosen vault's script fields while preserving owner keys and execution counts. Saving there changes the live vault used by that vault's loader.

## Discord bot and control panel

The Discord Control page is available at `/discord.html` and is linked from the authenticated Admin dashboard. It uses the existing admin session and stores channel IDs, editable channel panel text, and IDs of bot-posted panels in Firestore. The Discord bot token is never returned to the browser or stored in Firestore.

This integration uses Discord HTTP interactions, so it does not need a continuously running bot process. Its guild commands are registered only for application `1563789940452622397` in guild `1563443676313559100`; the interaction handler independently rejects interactions from all other guilds and validates Discord's Ed25519 request signature. The configured channels are Rules, Notices, Features, Top-Globals, Chat, Suggestions, Site, Blacklist, Bypass, and Commands. `/help`, `/panel`, `/scripts`, and `/verify` work throughout the allowed guild. Channel commands are limited to their mapped channel after a channel ID is entered in Discord Control. The `/bypass` response only directs users to legitimate access help; it does not bypass a protection or verification check.

To connect the bot after deployment:

1. In the Vercel project settings, add `BOT_TOKEN` as a private environment variable and redeploy. The server also accepts the older name `DISCORD_BOT_TOKEN`. Never put this token in HTML, client JavaScript, a commit, or a chat message.
2. In the Discord Developer Portal, install the application into the specified server with the `bot` and `applications.commands` scopes. Grant the bot only the permissions it needs; publishing channel panels requires Send Messages and Embed Links in those channels.
3. In the app's General Information settings, set the Interactions Endpoint URL to `https://voidedx.vercel.app/api/discord-interactions`. The app's public key is already configured in the server handler. Discord validates the endpoint with a signed PING request.
4. Sign into `/admin.html`, open Discord Control, enable Developer Mode in Discord, right-click each text channel and choose Copy Channel ID, then enter the IDs and save.
5. Click Register commands, then Publish channel panels. Publishing updates the bot's prior panel message when possible; otherwise it sends a new one.

`/verify vault_id:<id>` opens the existing VoidedX vault access page. It does not link a Discord account to a website/Firebase account or assign Discord roles. Those require an additional OAuth and role-management integration; website key-page verification does not by itself prove Discord membership.

### Discord `/obfuscate` and void tokens

`/obfuscate` creates a private obfuscation link with **5 void tokens**. The command takes an optional `.lua`/`.txt` attachment or pasted `code` plus an optional `level`, and replies with an ephemeral embed containing a link in the form `https://voidedx.vercel.app/obfuscation?vx=<token>` (the `/obfuscationvx=<token>` rewrite also works). Opening the link preloads the uploaded source or pasted code, and each successful obfuscation consumes one token. When the 5 tokens are gone the page stops and tells the user to run `/obfuscate` again.

Sessions live in `obfuscationSessions/{token}` and `obfuscationSessionOwners/{discordUserId}`. Tokens are 192-bit random `base64url` values, expire after 7 days, and a user has one active link at a time: running `/obfuscate` again refreshes that link's source, keeps the same token while credits remain, and deletes the previous session document once a new token is issued. Token spends use a Firestore transaction, so two browser tabs cannot spend the same last token twice. Expired sessions are deleted when read, and `GET`/`POST /api/obfuscation-session` return 404/410/403 with a message instead of a stack trace.

The page downloads the generated `.lua` and can also save the generated copy to a new vault. Saving uses Firebase anonymous auth and the same Firestore schema as the Creator Panel: `encodeVaultSource` for the source, `encodeObfuscatedCode` for the execution copy, `obfuscationEnabled: true`, and the standard 10-hour auto-delete. Vault saving is subject to the same 5-vault and Firestore document-size limits, and the vault is owned by the anonymous browser session, so the page shows the guest-recovery note; a user who clears browser storage loses the ability to edit that vault from the panel. No Discord account is linked, so a leaked link can be used by anyone who has it until its tokens run out or it expires.

## Loader and key protection

The copied loader keeps the stable `loadstring(game:HttpGet(".../api/raw?id=..."))()` form and contains no token query parameter or format flag. Executor requests to `/api/raw` receive the bootstrap by default; normal browser requests are redirected to the vault page. Each `/api/raw` fetch mints a new signed 10-second loader token and encrypts the returned bootstrap with a token-derived seed; that bootstrap rechecks the token when run. A copied bootstrap body expires, while the token-free outer URL can fetch a new bootstrap whenever the vault remains available. Owners can increment the vault version to invalidate already-issued bootstrap bodies, pause the vault to block new launches, or revoke a key to block future keyed access. Each successful `/api/verify` call also issues a cryptographically random, one-use delivery ticket; it expires after the vault's configured 20, 30, 45, or 60 seconds (45 by default) and `/api/payload` consumes it once while rechecking the vault, key, player binding, ban, IP-lock state, and pause status. Keyed verification limits can be set to 5, 10, 20, 30, or 50 checks per network in 15 minutes (30 by default); the counter includes successful checks. Pausing does not stop a script that has already been downloaded and is running. Newly generated keys use 16 cryptographically random characters; existing keys continue to work. Loader tokens minted by `/api/raw` are bound to the requesting network by default; set `LOADER_TOKEN_IP_BIND=0` if an executor's HTTP egress IP changes between the bootstrap fetch and its token-check gate. `LOADER_TOKEN_SECRET` may be set to a random secret of at least 32 bytes; if unset, signing and seed derivation use `ADMIN_SESSION_SECRET`, then `FIREBASE_SERVICE_ACCOUNT`.

Generated loaders no longer ship the inner loader as plaintext inside the response. The bootstrap is encrypted with a token-derived Xorshift32 keystream, and the seed is released only by a separate `/api/raw?...&format=token-check` gate request after the token, network binding, vault version, key, and pause checks pass. A captured bootstrap body therefore cannot be decrypted offline without a live, valid gate request. The gate and every delivery request are logged against a per-session trace.

Payload delivery is split between two requests. `/api/verify` returns a random seed, a shuffled chunk order, a CRC32, and a 16-hex trace; `/api/payload` returns only the shuffled, encrypted chunks. Capturing either response alone does not yield the script. The runtime compares `game.HttpGet`, `loadstring`/`load`, `HttpService.JSONDecode`, `string.char`/`byte`/`sub`, `table.concat`, `pcall`, `rawequal`, and `debug.info` against references captured at start. Swapped functions are reported to `/api/integrity`; high-confidence flags mark the one-use ticket blocked, so `/api/payload` refuses delivery, and every report is stored with the trace, vault, player, IP, and user agent. Each payload begins with a `--[[vx:TRACE]]` watermark, and `loaderDeliveries/{trace}` maps it to the vault, player, key issue, and delivery IP for leak forensics. The optional fast-load plaintext cache is not used by shielded loaders because an on-disk plaintext copy defeats the protection.

This raises the cost of casual `HttpGet`/`loadstring` dumping and makes leaks attributable, but it is not DRM. Code that a client can execute can be captured by a runtime that is already compromised, for example a hook installed before the loader starts, an executor that patches `game:HttpGet`, or a modified loader that strips the checks. Keep secrets and private API credentials out of client scripts.

Each generated inner loader starts with a `-- VoidedX Loader [https://voided.vercel.app]` comment and prints `[VoidedX] VoidedX Protection - protect your scripts at https://voided.vercel.app` followed by an ASCII progress bar in Roblox's F9 Developer Console while the execution copy is downloaded, checked, and compiled, for example `[VoidedX] [=======-------]  50%  Downloading payload`. The credit line appears only after the gate decrypts the inner loader; the `/api/raw` response itself stays ciphertext plus decoder. The percentage is an estimate because `game:HttpGet` does not expose byte-level download progress; it stays below 100% until the response arrives and reaches 100% when the script is ready to start.

## Vault protection and obfuscation

Vault Protection runs the VoidedX engine in the browser; Prometheus is no longer part of the build. The engine compiles the script to register bytecode instead of wrapping its text. A Luau parser produces an AST, the compiler lowers it to 8-byte instructions (opcode, 8-bit register A, two 24-bit operands), and the program is serialized to a binary blob with all constants, including strings, inside it. That blob is LZSS-compressed, encrypted with layered LCG-derived additive masks, split into independently encoded segments, and delivered with a bundled interpreter that executes the bytecode. The original source is gone the moment compilation finishes: the output contains no `loadstring` of user code and no plaintext source, so a dumper cannot recover it by grabbing a chunk argument. Opcode numbering is shuffled per build, the interpreter handlers are emitted in a random order, and function/local names are randomized.

Strengths are Fast, Low, Medium, High, and Absolute. Higher strengths split the payload into more segments, add encryption layers, spend more effort on compression matching, and inject more decoy functions; Low and above also turn on the integrity gate, and High and Absolute additionally flag installed debug hooks. Auto selects High up to 16 KiB of UTF-8 source and Medium above that, and owners can override the selection. Extra transforms adds decoy code and more encrypted segments. The runtime shield verifies the decompressed length, an Adler32 checksum, and a weighted checksum over the compressed payload before parsing it, and high-confidence integrity failures return an error instead of falling back to running anything. Builtin references (`string.byte`/`char`/`sub`/`len`, `table.concat`, `rawequal`) are captured at start and compared at both gates, so replacing them to intercept the decode path is detected. Stronger settings take longer and produce larger output; Absolute is the slowest. Keep a readable backup and test the generated copy in a private place before replacing a live vault. Obfuscation errors stop saving before Firestore is updated, leaving the prior vault unchanged. The `HttpService:JSONDecode(response)` call in the loader parses the server's JSON envelope; `res.json()` escapes the delivered source correctly. It is not a way to hide client code: any code delivered to a client for execution can be captured at runtime.

Closures compile to real Lua functions that call the interpreter with their own captured cells, so `pcall`, `table.sort` comparators, coroutines, and callbacks handed to Roblox APIs behave normally. Because execution goes through an interpreter, the generated copy runs slower than the original source, typically several times slower; test frame-sensitive scripts before replacing a live vault. Compiler limits are explicit and reported before saving: 255 registers per function (large multi-assignments are staged through tables to stay inside that limit), about 16.7 million instructions per function, and about 16.7 million constants per function. Vaults saved by the older LZSS/Loadstring engine (including Prometheus-generated copies) are marked with an older obfuscation profile; open and save them again to regenerate the execution copy.

Source up to 128 KiB is stored as readable text in Firestore for owner audits; larger source is gzip-base64 compressed to preserve Firestore document space. Compression is not encryption. Older plain-text and gzip-base64 records remain supported, and loading a vault decodes compressed source into the editor. The execution copy is stored as plain text when it is ASCII and smaller than its gzip-base64 form, otherwise gzip-base64; the API decompresses base64 records before delivery. Browser previews accept source up to 4 MiB and generated output up to 32 MiB; saving source to a vault remains capped at 2 MiB. Outputs above 1 MiB are download-only so a very large string does not freeze the editor. Saved vault copies are limited to 4 MiB and each vault document is kept below an estimated 870 KiB; the combined source and execution copy can hit the document limit first. Large scripts can take several minutes to process or time out. Re-saving unchanged source with the same strength and protection settings reuses the last generated copy in that browser session.

The engine raises the cost of static reading and casual dumping, but it is not DRM. A runtime that is already compromised can still capture the script after decoding, for example through a hook installed before the wrapper starts. Keep private API credentials and secrets out of client scripts; the loader shield and server-side vault checks remain the enforcement boundary.
