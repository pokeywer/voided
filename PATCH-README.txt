Flow: the outer loadstring still fetches /api/raw with no token. The response carries the inner loader only as Xorshift32 ciphertext. It opens with an ASCII VOIDEDX LOADER banner; the gate URL, which embeds the live token, is stored as ciphertext under a per-build key instead of a readable literal, and every generated local name is randomized per build. Before the gate request and again before decrypting, the bootstrap checks the captured identity of string.byte/char/sub/gsub/match, table.concat, pcall, error, type, math.floor, loadstring/load, string.dump, game.HttpGet and, when present, bit32, getgenv/getfenv/setfenv, also compares the loadstring/load entries seen through getfenv(0) and getgenv() against the captured ones so a wrapper installed in only one channel is caught, and probes string.dump against both compile entries: a native load rejects a dumped Lua function while a Lua-level wrapper accepts it, which exposes hookfunction(loadstring, ...) shims that forward to the original. It refuses to continue if one was swapped or a debug hook is active, and it installs a debug.sethook function-count watchdog that rechecks the same references and its own hook identity for the first ~16M instructions or 10 seconds, marking itself in getgenv()._vxwd so the armor accepts it; both denials exit with "Voided: Doing this is not allowed." The plaintext is scrambled before sealing: locals and parameters are renamed, string literals move into a per-run encoded table decoded in memory, and the body is minified, so only the -- VoidedX Loader credit comment stays readable. Compilation prefers whichever of loadstring/load is still native and, when the executor supports a function reader, feeds the decode entry 4096-byte chunks instead of one string, so an argument logger on the compile entry sees fragments. A separate token-check request releases the HMAC-derived seed. It answers from the signed ticket alone, so no database read sits in front of a loader start; /api/verify and /api/payload still enforce pause and ban state, so a live ticket for a paused vault still cannot deliver. A reply is accepted only in the exact vx1|<8 hex>|<16 hex> shape, so a near-miss reply is treated as expired and a captured response body still cannot be decrypted offline. The candidate gate URLs, the live one shuffled among decoys, are all launched at once through task.spawn and the loader resumes as soon as one reply parses; a blocking HttpGet simply runs them in order. /api/verify returns a one-use delivery ticket, a per-session key, and a 16-hex trace. The ticket is stored with hashes of the requester's address and client signature plus the player ID, place ID, and issue time; /api/payload accepts it once, only from that same connection, then deletes it. The payload response carries the encrypted parts in order and a CRC32 of the ciphertext, never a checksum of the plaintext, so a captured response cannot confirm a decode. Decoding is byte-oriented: a byte-keyed alphabet map, four characters per string.byte read and four bytes per string.char write, with the CRC32 accumulated during the same pass, and the XOR keystream advances once per 32-bit word. The loader checks the boot marker on the first part before it decodes the rest, then the ciphertext checksum before decrypting and the --[[vx:TRACE]] watermark after, so a session key only opens the copy it was issued with. Capturing either response alone is not enough. The runtime compares game.HttpGet, loadstring/load, HttpService.JSONDecode, string.char/byte/sub, table.concat, pcall, rawequal, debug.info, print, tostring/tonumber/type/next/ipairs/setmetatable/rawset, math.floor, string.format/rep/gsub/match, game.GetService, HttpService.UrlEncode, task.wait/spawn, and, where the executor provides them, string.dump, error, debug.sethook/gethook and getfenv/setfenv against references captured at start. It also cross-checks the bootstrap's getgenv()._vxwd marker against debug.gethook, so a hook installed after the watchdog expires reports hook_installed; those late-swap and foreign-hook flags are recorded for admins but are not blocking, so an executor or another script touching its own globals mid-session is not locked out. If reader-mode compilation returns nothing the loader retries the full string and then the other compile entry, and an unshield failure now reports its actual reason instead of an empty flag list. Before the payload is requested it also publishes a decoy getgenv().VoidedX table whose unlock/bypass/dump helpers and unknown-field reads report honeypot_triggered, a blocking flag. Swapped functions are reported to /api/integrity, and high-confidence reports mark the one-use ticket blocked so /api/payload refuses delivery. Every payload carries a --[[vx:TRACE]] watermark; loaderDeliveries/{trace} maps it to the vault, player, key issue, and delivery IP. The fast-load plaintext cache is bypassed for shielded payloads because an on-disk plaintext copy defeats the protection. Set LOADER_TOKEN_IP_BIND=0 if legitimate executor HTTP egress IPs change between the bootstrap and gate requests; set LOADER_TOKEN_SECRET to a random value of at least 32 bytes for stable signing and seed derivation; set DELIVERY_TICKET_BIND=0 only if executor HTTP egress addresses change between the verify and payload requests. These checks raise the cost of runtime dumping and make leaks attributable, but they are not DRM: a caller that runs the whole flow still receives every part and the key that opens them, and a hook installed before the loader starts, a patched executor, or a loader modified to strip checks can still capture executed code.

This patch uses the bundled Prometheus fork locally in the browser and then repacks its output in the VoidedX armor container, so delivered copies do not carry Prometheus's recognizable layout. It does not include the separate Prometheus website interface.

The strength selector offers Fast, Low, Medium, High, and Absolute in Luau mode. The Prometheus fork starts in a module worker and compiles the script to VM bytecode, then lua-voidedx-armor.js repacks that output: the watermark is rebuilt from split literals, helper names are renamed, decoys and opaque guards are added, and the payload is LZSS-compressed, masked in passes, split into shuffled segments, and wrapped in a randomized loader with integrity checks and a Roblox gate. The loader itself is emitted unformatted: comments are stripped, statements are packed with minimal gaps, and line breaks land at random so the file reads like raw VM output. Every armor level now emits the debug-hook guard, which accepts a hook only when getgenv()._vxwd names it: the bootstrap watchdog passes, a foreign hook or stale marker is denied. Nested containers compile from a per-build reader (1-6 KiB pieces, under the table.unpack result cap Luau and Lua 5.4 enforce) and prefer whichever of loadstring/load is still native, falling back to one assembled string when the loader rejects function chunks. Profile 18 goes after runtime capture, which is how a dump is normally produced. The loader collects candidates from loadstring, load, _G.loadstring, _G.load, and the load/loadstring fields of getfenv(0), getgenv() and getrenv(), then keeps the first one that debug.info/debug.getinfo still reports as a C function (what == "C", or "[C]" on Luau); a hookfunction(loadstring) or hookfunction(load) proxy is a Lua closure and is rejected before any payload passes through it. The same native check covers pcall, error, rawequal, string.byte, string.char, string.sub, string.len, table.concat, table.unpack and math.floor, because trapping a decoder captures a chunk just as well as trapping the loader; it runs before decoding, after decoding, and immediately before the compile call. The engine's eai_* identifier family, the cheapest fingerprint for a reader that recognizes the engine, is redrawn per build before compression (757-1354 occurrences per copy, zero after), renaming locals, upvalues and shadowing consistently so behavior is unchanged. A missing executor primitive reports a different message from a failed start. Profile 19 removes the last place where the chunk existed as one string: the inflater is a pull iterator that keeps only the 64 KiB window and the token position and returns at most one 1-8 KiB piece per call, resuming mid-run across piece edges, so the plaintext is only ever the piece load is parsing and a debug.getupvalue on the reader yields the compressed stream and the window, not the source. Roblox's loadstring compiles strings only, so there the loader requires a working string compile, detects reader support separately and concatenates the pieces just before compiling; nothing is gated on function chunks. The loader also clears the debug hook for the decode and compile and restores it just before the payload runs, so a dumper that satisfies the getgenv()._vxwd marker with its own hook sees nothing while the copy is readable. Tampering, integrity failure and a failed compile share one message, and the vx_probe string is gone. The engine anti-tamper probes lost their readable tokens as well (empty failure message, a string.char-built VoidedX tag, a number-only concat probe), so a dump no longer names the checks it still has to satisfy. Each delivered copy now starts with an ASCII VOIDEDX OBFUSCATION banner and 16 to 29 inert `do ... end` junk blocks, followed by the `-- VoidedX` marker. The junk is regenerated per build from confusable identifiers (l/I/1, O/0/o, S/5, Z/2, B/8, G/6, q/9), randomized block shapes, number and escape soup, and gibberish comments, so it reads as noise and no two builds share the same preamble. Fast, Low and Medium use the Medium preset; High and Absolute use Strong. No level uses the readable Weak preset, so every copy reaches the VM. Every level keeps one Prometheus VM layer: a second Vmify pass over the first VM's bytecode corrupted output in every interpreter we tested. Depth comes from nested VoidedX containers instead (Fast 2, Low 3, Medium 5, High and Absolute 6), capped by payload size so large copies stay storable. Low and above add the Sigil Cipher (integer-exact string sealing), a seed-bound VoidedX watermark, decoys, and anti-tamper. The loader also rejects a `pcall` that swallows errors. Absolute also turns on tamper checking and extra string splitting. Builds can additionally override the container count (1-6 layers), switch the junk preamble off or to heavy, disable the gibberish comments, and pick the compact layout; the defaults reproduce the profile 19 shape. Auto uses High up to 16 KiB of UTF-8 source and Low above. The page rewrites bare `#` length operators in the generated decoder to a safe helper so executors that return userdata objects do not crash. Obfuscation failures stop saving and preserve the existing vault. Source up to 128 KiB is stored as readable text in Firestore for owner audits; larger source is gzip-base64 compressed to preserve document space, not encrypted. Older plain-text and gzip-base64 records remain supported. The execution copy is stored as plain text when it is ASCII and smaller than its gzip-base64 form, otherwise gzip-base64; the API decompresses base64 records for delivery. Browser previews accept source up to 4 MiB and generated output up to 32 MiB; saving source to a vault remains capped at 2 MiB. Output above 1 MiB is download-only to avoid freezing the page. Saved outputs are capped at 4 MiB, and the estimated Firestore document cap is about 870 KiB, so the document cap can be reached first. Obfuscation jobs may take several minutes; Absolute is the slowest and most fragile. Unkeyed raw loaders fetch the generated body rather than embedding a second copy inside the bootstrap. Existing /api/raw, /api/verify, and /api/payload routes deliver it. Client code can still be captured and analyzed while running.

Obfuscation profile 18 marked an earlier container: an ASCII VOIDEDX OBFUSCATION banner and a per-build block of inert, confusable-identifier junk on top, a VoidedX marker with an intentionally unformatted loader body, the integer-exact Sigil Cipher replacing the stock string step, a tolerant anti-tamper probe suite plus a loader-level `pcall` guard, a debug-hook guard at every armor level that honors the bootstrap's getgenv()._vxwd marker, reader-mode compilation in nested containers, and a single Prometheus VM layer with nested VoidedX containers at every strength. Profile 17 replaced the fixed container codec with a polymorphic one: each build chooses its own byte mixer (add, subtract, or affine with a modular inverse), its own 32-bit state-chain multiplier, increment and content-mix weights, its own keystream shift, its own LZSS token split point, minimum match length, offset byte order, offset bias and flush sizes, its own identifier style, and its own segment permutation, which is rebuilt at runtime from a seed instead of being shipped as a table. The keystream also mixes the previous ciphertext byte and the absolute stream position, so one segment cannot be decoded in isolation, and two builds of the same script share no constant, no identifier and no decode shape; a deobfuscator written for one file does not work on the next. Profile 18 targets the runtime capture path, which is how a dump is actually produced: the loader now keeps only a compile entry that `debug.info`/`debug.getinfo` still reports as native, so a `hookfunction(loadstring)`/`hookfunction(load)` proxy is rejected before the payload reaches it, the same check covers the decode primitives a capturer would trap, the compile is fed through a per-build 1-8 KiB reader, and the engine's `eai_*` identifier family is redrawn per build. Vaults saved before it, including the profile 17 build, the profile 16 build, the profile 15 build, the profile 14 build, the two-layer High/Absolute VM build, bytecode-VM (profile 10), unarmored copies (profile 11), and the earlier armor (profile 12), carry an older profile number. The VM keeps the Prometheus opcode set because the engine is a prebuilt binary with no source to renumber it, so the armor hides the engine layout but a recognizable bytecode dump can still be disassembled with the Prometheus tooling. The profile 18 and 19 checks raise the cost of runtime capture rather than closing it: an executor that also hooks `debug.info`/`debug.getinfo`, or swaps the `debug` table before the loader reads it, can make a wrapper look native, a line hook installed before the run still watches the setup lines and the payload execution, and a full-privilege run can still be traced or reimplemented from behavior. Open and save older vaults again to regenerate the execution copy. Keep a backup and try the output in a private test place before broad use. A saved vault document is capped at an estimated 870 KiB to leave headroom under Firestore's document-size limit. Profile 20 fixes a miscompile that only showed above High strength and closes the last plaintext delivery path. The number-expression step could rebuild a large integer through modulo chains that crossed 2^53, where LuaU's doubles stop being exact, so one VM operand index evaluated to a different value than the pipeline intended and a branch flipped at runtime (the visible symptom was "attempt to concatenate nil with string"); generated expressions are now capped at 2^40, with a plain literal above that. Saves carry the new profile number, so older vaults are flagged and rebuilt when saved again. On the delivery side, /api/payload now only answers with the shielded form (ciphertext parts plus a tag over the ciphertext) and refuses a ticket that has no shield, so the route no longer returns the execution copy as plaintext; the loader likewise rejects any payload that is not v5.

The inner loader obfuscator is now scope-aware instead of using one flat name table: bindings are tracked per block (locals, loop variables, parameters, local function, nested blocks, repeat/until, elseif/else, method definitions), references resolve to the innermost visible binding, and globals, table keys and ./.. fields are never renamed. This removes a class of silent behaviour changes where a shadowed local was merged with the variable it shadowed. Verified on a 17-case corpus with matching output between original and obfuscated, plus the full delivery harness. No profile change: the loader is generated per fetch, not stored with the vault.

Loader build 7 adds a second lock before the code is released. /api/verify now rejects any request without a delivery attestation, a server-side MAC over the loader token and the vault id that is sealed inside the bootstrap /api/raw served; the route recomputes it, compares it in constant time, then validates the embedded token itself (signature, vault, key fingerprint, vault version, UTC day, ten-second lifetime, network binding). The session records that it was attested and /api/payload refuses a ticket that was not. Releasing the script now needs two independent approvals: a key without a bootstrap gets no ticket, and a captured bootstrap without the key gets nothing. The copied loader line, the gate protocol and stored vault data are unchanged, so no re-save is needed. The loader stamp reads --voidedx-loader-p30-b7.

Loader build 6 (delivery bootstrap only, no profile change, no vault rebuild needed): each gate URL is sealed in two halves under two different keys, cut inside the token itself, so no decoded blob ever holds the whole credential and the runtime joins the halves. The gate request also carries the UTC day the loader was minted for (d) and an eight-character key fingerprint (kh); the server rejects a token whose signature disagrees with the presented day or key hint, and a token is now invalid once its UTC day has passed on top of its ten-second lifetime. Decoys carry the same shape with their own fingerprint and a plausible nearby date, so a request log does not mark the live entry. The bootstrap and the obfuscated copy each print their version on the first line and in the banner (--voidedx-loader-p30-b6, profile 30 build 6).

Obfuscation profile 30 is the current container. The step program is now built in one of two shapes per build: the linear dispatcher (read in order, relabelled while it runs) or a chained dispatcher where each step stores the byte index of its successor and the pairs are scattered, so file order is not execution order and the entry point varies too. Half of builds get each shape; a chained program adds 12 bytes, not another engine, so sizes are unchanged. Identifier generation added two confusable styles (names built only from l/I/1, O/0/o, S/5, Z/2, B/8, G/6, q/9 - the l0li0lil0ili0 look) for loader names as well as filler. Container depth stays at six layers: eight measured 460-590 KiB on a ten-line script, which is the heaviness to avoid. Validated on 30 single-layer builds (15 chained, 15 linear), the 10-variant level matrix in Lua 5.4 and LuaU, 8 real Prometheus outputs and the full delivery harness.

Obfuscation profile 29 changed the container. The loader dispatcher relabels itself while it runs (it swaps the next two steps in the handler table and the matching program bytes every few steps, so a live dump of the table never matches what executes), refuses a run that exceeds an os.clock budget, and the same devices plus interleaved state-machine filler are in the delivery bootstrap. The bootstrap mints a per-fetch session id and, only when the executor exposes writefile/readfile/isfile, writes a marker file that holds nothing but that id - no payload, key or token is ever written to disk. Key and session binding stay in the delivery layer (ticket, IP-bound token, per-session seed), and every vault's loader refuses a non-Roblox interpreter before any request.

Obfuscation profile 28 added a debug-independent hook detector: on hosts where string.dump rejects native C functions, a successful dump of a captured builtin proves it is a Lua closure, so a wrapped load/loadstring, pcall, error, table.concat, type or string.char is refused without asking debug.info. The probe calibrates itself on string.byte first and stays silent where dumping is permissive. It runs in both the armor loader and the delivery bootstrap and costs a handful of pcall calls at start.

Obfuscation profile 27 turned the loader runtime into a program: the integrity gate, decode, compile-entry probe, inflate, chunk compile, chunk-name tripwire, post-compile re-check and hook restore are closures in a shuffled table under per-build opcode numbers, executed from a sealed byte program that is checksummed before the first step runs (with two no-op steps mixed in). Every nested container carries its own program, so Absolute runs it inside all six layers, and the filler blocks are interleaved between steps. Size is unchanged in practice (about 36-44 KiB at Fast, 217-260 KiB at Absolute on a small script), because the program replaced statements rather than adding another engine; the single Prometheus VM layer stays single because stacking Vmify breaks real scripts.

Obfuscation profile 26 added the anti-tamper probes. The loader additionally refuses a replaced load/loadstring that answers a nil chunk and a replaced string.char that casts out-of-range values, on top of the native-identity checks, the two-channel environment consensus, the watch-only hook requirement, the chunk-name tripwire and the per-build canary. Filler is interleaved between the loader's own helper blocks (one to three state or register machines after a block) rather than only in front of the file, and volume was reduced on purpose: normal 12-21 blocks, heavy 26-39, scaled by strength. Strength still comes from one Prometheus VM layer wrapped in sealed VoidedX containers behind a live delivery ticket, not from padding; a reader who controls the interpreter can still reach the payload.

Obfuscation profile 25 made the delivered copy physically large: the junk preamble now includes generated state machines (state id, accumulator, four to seven states, branch thresholds that are sometimes unreachable) and four-register byte machines with embedded instruction lists, each a multi-line do/end block that only touches its own locals. Counts scale with strength and with the junk setting (normal or heavy); measured overhead is about 8-28 KiB at normal and 24-61 KiB at heavy. It is padding, not protection: the VM, the sealed containers and the delivery gate are what stop a reader, and volume only raises the reading cost. Profile 25 also orders the loader so the Roblox check runs after the message helper it calls is defined.

Obfuscation profile 24 changed the delivery bootstrap as well as the armor. The bootstrap is no longer a flat script: each step is a generated handler, the handlers sit in a shuffled table under per-build opcode numbers, and the run order is a sealed opcode program that is checksummed before it runs, so the probe-decrypt-compile sequence is data instead of readable code. Every sealed blob passes through a per-build 256-byte substitution box after the keystream, part keys chain on the checksum of the previous decoded part so the parts only open in order, and a tail marker rejects a truncated body next to the head marker that rejects a wrong seed. The bootstrap carries no explanatory comments; only the VoidedX banner and the `-- VoidedX Loader` credit remain. The armor loader is laid out per build too: helper blocks are emitted in a dependency-safe shuffled order, loops are drawn as `while` or numeric `for`, the loader cross-checks the same builtin through `getfenv(0)` and `getgenv()` before decoding so a wrapper on one channel disagrees with the other, it rejects a compiled chunk whose `debug.info` source name is neither the requested name nor a host-provided value, and it verifies a canary byte at a random offset of the compressed stream, which catches a patched length or checksum branch. The bootstrap is built per request and is not stored with a vault, so every existing vault serves the new bootstrap on its next fetch without being re-saved; only the stored protected copies carry the profile number, and older ones keep launching until the owner saves them again.

REBUILDING OLD VAULTS: the delivery bootstrap is generated per request, so every vault already serves the newest loader; only its stored execution copy is tied to the profile it was saved with. In the admin panel, Vault source manager, use the new 'Rebuild outdated copies' button: it lists every obfuscated vault below the current profile, re-obfuscates each stored source at that vault's own strength and protection flags, replaces the live copy, skips vaults that are already current, and keeps going when one vault fails. Vaults that are running now keep their old copy until the rebuild reaches them, and each rebuilt vault invalidates loaders that were already issued for it, so players need to paste their loader again.

VOID TOKENS: 8 PER DAY

Every account gets 8 void tokens per day for the obfuscator. A token is spent after a copy is generated; the allowance resets at 00:00 UTC and does not bank. Admins can add bonus tokens, which are spent after the daily ones and never expire, or clear an account's bonus balance from Admin → Void tokens.

Signing out and back in no longer refreshes the allowance. The server builds the subject from the verified ID token, and obfuscationTokenAliases/{sha256(email)} points every account that proves the same verified email at one web:<firebaseUid> ledger, so a new session or a different provider (email/password, Google, Discord) with the same verified email merges into the existing counter instead of starting a fresh 8. Unverified password addresses and unlinked accounts stay keyed by UID, and the browser never chooses the subject.

The site now requires an account. site-auth.js mounts a login gate on every visitor page (dashboard/editor, obfuscator, community scripts, key system, Creator Panel, staff, Get-Key, leaderboard, vault view) with email/password, Google, or Discord, and pages no longer start guest sessions; the admin and Discord panels keep their existing admin login. The public page (/obfuscation) needs no link and spends the signed-in account's balance through /api/obfuscation-tokens, which now rejects anonymous sessions. When the browser still holds a leftover anonymous Firebase session, signing in calls /api/claim-guest-vaults: the server verifies both ID tokens and moves every vault owned by the guest UID onto the signed-in account, so the vaults appear immediately in the editor and Creator Panel. Linking instead (email sign-up, Google, or Discord on the guest session) keeps the same UID, so no move is needed. The gate also offers a forgot-password view that sends a Firebase reset email, and it sets browserLocalPersistence before subscribing to auth state, so a deploy or browser restart keeps the user signed in. /obfuscate in Discord still issues a private link of the form https://voidedx.vercel.app/obfuscation?vx=<token> (with the /obfuscationvx=<token> rewrite) that uses the user's Discord balance; upload a .lua/.txt file or paste code in the command, or open the link and paste it there. Both paths expose strength, armor layers (1-6 or the strength default), junk preamble (off/normal/heavy), gibberish comments, messy or compact layout, tamper check, and extra string splitting, and the page can still save the generated copy to a new vault. The page was rebuilt with segmented controls and switches instead of native selects, a token card that draws one segment per daily credit, a live source readout (characters, lines, bytes), result stats (size, characters, lines, build time) plus a chip row of the settings used, remembered build choices with a Reset button, Paste/Clear source tools with a confirmation dialog, Ctrl/Cmd+Enter to build, and the English/Português do Brasil switcher from i18n.js.

New Firestore collections: obfuscationTokens/{subject} keeps the daily counter and bonus balance, where subject is discord:<userId> or web:<firebaseUid>; obfuscationTokenAliases/{sha256(email)} maps a verified email to its web ledger so sign-out/sign-in and provider switches share one allowance; obfuscationTokenGrants/{autoId} is the admin grant history. obfuscationSessions/{token} keeps the preloaded source, level, filename, and expiry, and obfuscationSessionOwners/{discordUserId} points to the user's current link. Link tokens are 24-byte base64url values and last 7 days; a user keeps one active link at a time, and running /obfuscate again refreshes its source and reuses the token. Spending and granting run in transactions, so a token cannot be double-spent and a bonus grant cannot be lost. GATE URLS ARE NOW ASSEMBLED PER REQUEST

api/_loaderSource.js (replaced)

The bootstrap used to decode every gate candidate up front into one table and then probe from it, so a single memory snapshot taken after that step yielded all four candidate URLs, the live one included. Each candidate is now kept as its two sealed halves and is decoded into a local inside the probe function, immediately before the HttpGet call, so a complete URL exists only for the microseconds around that one request. The old up-front pass was replaced by a shape check on the sealed table, which also denies a tampered or truncated candidate list. What this does not change: whoever hooks game.HttpGet still sees the live URL at the moment it is called, because the client has to send it. LOADER PROGRAM IS NOW AN OPERAND STREAM WITH A PRESENCE DIGEST (route 3, step 1)

api/_loaderSource.js (replaced)

The bootstrap's sealed program used to be one byte per step with no operands, so a reader could delete any cell it judged unreachable and nothing changed. Every instruction now carries an operand byte, decoy cells are interleaved before the terminal step, and the operands fold into a running total that the terminal handler verifies before it runs the payload. Trimming, inserting or corrupting cells changes the total and the loader denies itself with the usual message. The operand bytes ride the same sealed, checksummed stream as the opcodes, so they are not readable without opening it, and the opcode numbering is still redrawn per build.

Verified: bootstrap 154/0 unarmored and 131/0 at the default 3 containers, delivery chain 96/0, Luau 4/0. Negative test - setting the expected total one off made every run deny with "Voided: Doing this is not allowed.", which proves the check gates execution instead of sitting in the file unused.

SERVER SIDE: /api/raw refuses a fetch whose user-agent is a known HTTP library, worker runtime or browser driver and answers 415 with the same Lua error as its body, so a terminal or a scraper handed the link gets nothing runnable: undici, node, node-fetch, axios, got, superagent, python-requests, python-urllib, urllib3, aiohttp, httpx, okhttp, Java, Go-http-client, curl, wget, libwww-perl, PostmanRuntime, insomnia, RestSharp, Faraday, workerd, Cloudflare-Workers, Vercel, edge-runtime, Deno, PhantomJS, headlessChrome, Selenium, Puppeteer, Playwright, NSUrlSession, Apifox, Apipost, Hoppscotch. /api/verify and /api/payload apply the narrower version of the rule, because that is where the game identity is proven and a phone executor's own HTTP backend can legitimately present a platform client: there curl, wget, okhttp, Java, NSUrlSession, httpclient, libwww-perl, Faraday, Apifox, Apipost and Hoppscotch are logged and not blocked, while server-side script runtimes are still refused.
