Flow: the outer loadstring still fetches /api/raw with no token. The response carries the inner loader only as Xorshift32 ciphertext. It opens with an ASCII VOIDEDX LOADER banner; the gate URL, which embeds the live token, is stored as ciphertext under a per-build key instead of a readable literal, and every generated local name is randomized per build. Before the gate request and again before decrypting, the bootstrap checks the captured identity of string.byte/char/sub/gsub/match, table.concat, pcall, error, type, math.floor, loadstring/load, string.dump, game.HttpGet and, when present, bit32, getgenv/getfenv/setfenv, also compares the loadstring/load entries seen through getfenv(0) and getgenv() against the captured ones so a wrapper installed in only one channel is caught, and probes string.dump against both compile entries: a native load rejects a dumped Lua function while a Lua-level wrapper accepts it, which exposes hookfunction(loadstring, ...) shims that forward to the original. It refuses to continue if one was swapped or a debug hook is active, and it installs a debug.sethook function-count watchdog that rechecks the same references and its own hook identity for the first ~16M instructions or 10 seconds, marking itself in getgenv()._vxwd so the armor accepts it; both denials exit with "Voided: Doing this is not allowed." The plaintext is scrambled before sealing: locals and parameters are renamed, string literals move into a per-run encoded table decoded in memory, and the body is minified, so only the -- VoidedX Loader credit comment stays readable. Compilation prefers whichever of loadstring/load is still native and, when the executor supports a function reader, feeds the decode entry 4096-byte chunks instead of one string, so an argument logger on the compile entry sees fragments. A separate token-check request releases the HMAC-derived seed after the token, network binding, vault version, and key checks pass, so a captured response body cannot be decrypted offline. /api/verify returns a random payload seed, a shuffled chunk order, a CRC32, and a 16-hex trace; /api/payload returns only the shuffled, encrypted chunks. Capturing either response alone is not enough. The runtime compares game.HttpGet, loadstring/load, HttpService.JSONDecode, string.char/byte/sub, table.concat, pcall, rawequal, debug.info, print, tostring/tonumber/type/next/ipairs/setmetatable/rawset, math.floor, string.format/rep/gsub/match, game.GetService, HttpService.UrlEncode, and task.wait/spawn against references captured at start. Before the payload is requested it also publishes a decoy getgenv().VoidedX table whose unlock/bypass/dump helpers and unknown-field reads report honeypot_triggered, a blocking flag. Swapped functions are reported to /api/integrity, and high-confidence reports mark the one-use ticket blocked so /api/payload refuses delivery. Every payload carries a --[[vx:TRACE]] watermark; loaderDeliveries/{trace} maps it to the vault, player, key issue, and delivery IP. The fast-load plaintext cache is bypassed for shielded payloads because an on-disk plaintext copy defeats the protection. Set LOADER_TOKEN_IP_BIND=0 if legitimate executor HTTP egress IPs change between the bootstrap and gate requests; set LOADER_TOKEN_SECRET to a random value of at least 32 bytes for stable signing and seed derivation. These checks raise the cost of runtime dumping and make leaks attributable, but they are not DRM: a hook installed before the loader starts, a patched executor, or a loader modified to strip checks can still capture executed code.

This patch uses the bundled Prometheus fork locally in the browser and then repacks its output in the VoidedX armor container, so delivered copies do not carry Prometheus's recognizable layout. It does not include the separate Prometheus website interface.

The strength selector offers Fast, Low, Medium, High, and Absolute in Luau mode. The Prometheus fork starts in a module worker and compiles the script to VM bytecode, then lua-voidedx-armor.js repacks that output: the watermark is rebuilt from split literals, helper names are renamed, decoys and opaque guards are added, and the payload is LZSS-compressed, masked in passes, split into shuffled segments, and wrapped in a randomized loader with integrity checks and a Roblox gate. The loader itself is emitted unformatted: comments are stripped, statements are packed with minimal gaps, and line breaks land at random so the file reads like raw VM output. Every armor level now emits the debug-hook guard, which accepts a hook only when getgenv()._vxwd names it: the bootstrap watchdog passes, a foreign hook or stale marker is denied. Nested containers compile from a per-build reader (1-8 KiB pieces) and prefer whichever of loadstring/load is still native. Profile 18 goes after runtime capture, which is how a dump is normally produced. The loader collects candidates from loadstring, load, _G.loadstring, _G.load, and the load/loadstring fields of getfenv(0), getgenv() and getrenv(), then keeps the first one that debug.info/debug.getinfo still reports as a C function (what == "C", or "[C]" on Luau); a hookfunction(loadstring) or hookfunction(load) proxy is a Lua closure and is rejected with the blocked message before any payload passes through it. The same native check covers pcall, error, rawequal, string.byte, string.char, string.sub, string.len, table.concat, table.unpack and math.floor, because trapping a decoder captures a chunk just as well as trapping the loader; it runs before decoding, after decoding, and immediately before the compile call. The engine's eai_* identifier family, the cheapest fingerprint for a reader that recognizes the engine, is redrawn per build before compression (757-1354 occurrences per copy, zero after), renaming locals, upvalues and shadowing consistently so behavior is unchanged. A modified runtime and a missing executor primitive now report different messages. Each delivered copy now starts with an ASCII VOIDEDX OBFUSCATION banner and 16 to 29 inert `do ... end` junk blocks, followed by the `-- VoidedX` marker. The junk is regenerated per build from confusable identifiers (l/I/1, O/0/o, S/5, Z/2, B/8, G/6, q/9), randomized block shapes, number and escape soup, and gibberish comments, so it reads as noise and no two builds share the same preamble. Fast uses the Weak preset; Low and Medium use Medium; High and Absolute use Strong. Every level keeps one Prometheus VM layer: a second Vmify pass over the first VM's bytecode corrupted output in every interpreter we tested. Depth comes from nested VoidedX containers instead (Fast 1, Low 2, Medium and High 3, Absolute 4), capped by payload size so large copies stay storable. Low and above add the Sigil Cipher (integer-exact string sealing), a seed-bound VoidedX watermark, decoys, and anti-tamper. The loader also rejects a `pcall` that swallows errors. Absolute also turns on tamper checking and extra string splitting. Builds can additionally override the container count (1-6 layers), switch the junk preamble off or to heavy, disable the gibberish comments, and pick the compact layout; the defaults reproduce the profile 18 shape. Auto uses High up to 16 KiB of UTF-8 source and Low above. The page rewrites bare `#` length operators in the generated decoder to a safe helper so executors that return userdata objects do not crash. Obfuscation failures stop saving and preserve the existing vault. Source up to 128 KiB is stored as readable text in Firestore for owner audits; larger source is gzip-base64 compressed to preserve document space, not encrypted. Older plain-text and gzip-base64 records remain supported. The execution copy is stored as plain text when it is ASCII and smaller than its gzip-base64 form, otherwise gzip-base64; the API decompresses base64 records for delivery. Browser previews accept source up to 4 MiB and generated output up to 32 MiB; saving source to a vault remains capped at 2 MiB. Output above 1 MiB is download-only to avoid freezing the page. Saved outputs are capped at 4 MiB, and the estimated Firestore document cap is about 870 KiB, so the document cap can be reached first. Obfuscation jobs may take several minutes; Absolute is the slowest and most fragile. Unkeyed raw loaders fetch the generated body rather than embedding a second copy inside the bootstrap. Existing /api/raw, /api/verify, and /api/payload routes deliver it. Client code can still be captured and analyzed while running.

Based on Prometheus by Elias Oelschner, https://github.com/prometheus-lua/Prometheus. See LICENSE-PROMETHEUS.txt.

Obfuscation profile 18 marks the current container: an ASCII VOIDEDX OBFUSCATION banner and a per-build block of inert, confusable-identifier junk on top, a VoidedX marker with an intentionally unformatted loader body, the integer-exact Sigil Cipher replacing the stock string step, a tolerant anti-tamper probe suite plus a loader-level `pcall` guard, a debug-hook guard at every armor level that honors the bootstrap's getgenv()._vxwd marker, reader-mode compilation in nested containers, and a single Prometheus VM layer with nested VoidedX containers at every strength. Profile 17 replaced the fixed container codec with a polymorphic one: each build chooses its own byte mixer (add, subtract, or affine with a modular inverse), its own 32-bit state-chain multiplier, increment and content-mix weights, its own keystream shift, its own LZSS token split point, minimum match length, offset byte order, offset bias and flush sizes, its own identifier style, and its own segment permutation, which is rebuilt at runtime from a seed instead of being shipped as a table. The keystream also mixes the previous ciphertext byte and the absolute stream position, so one segment cannot be decoded in isolation, and two builds of the same script share no constant, no identifier and no decode shape; a deobfuscator written for one file does not work on the next. Profile 18 targets the runtime capture path, which is how a dump is actually produced: the loader now keeps only a compile entry that `debug.info`/`debug.getinfo` still reports as native, so a `hookfunction(loadstring)`/`hookfunction(load)` proxy is rejected before the payload reaches it, the same check covers the decode primitives a capturer would trap, the compile is fed through a per-build 1-8 KiB reader, and the engine's `eai_*` identifier family is redrawn per build. Vaults saved before it, including the profile 17 build, the profile 16 build, the profile 15 build, the profile 14 build, the two-layer High/Absolute VM build, bytecode-VM (profile 10), unarmored copies (profile 11), and the earlier armor (profile 12), carry an older profile number. The VM keeps the Prometheus opcode set because the engine is a prebuilt binary with no source to renumber it, so the armor hides the engine layout but a recognizable bytecode dump can still be disassembled with the Prometheus tooling. The profile 18 native check raises the cost of runtime capture rather than closing it: an executor that also hooks `debug.info`/`debug.getinfo`, or swaps the `debug` table before the loader reads it, can make a wrapper look native, and a full-privilege run can still be traced or reimplemented from behavior. Open and save older vaults again to regenerate the execution copy. Keep a backup and try the output in a private test place before broad use. A saved vault document is capped at an estimated 870 KiB to leave headroom under Firestore's document-size limit.

VOID TOKENS: 8 PER DAY

Every account gets 8 void tokens per day for the obfuscator. A token is spent after a copy is generated; the allowance resets at 00:00 UTC and does not bank. Admins can add bonus tokens, which are spent after the daily ones and never expire, or clear an account's bonus balance from Admin → Void tokens.

Signing out and back in no longer refreshes the allowance. The server builds the subject from the verified ID token, and obfuscationTokenAliases/{sha256(email)} points every account that proves the same verified email at one web:<firebaseUid> ledger, so a new session or a different provider (email/password, Google, Discord) with the same verified email merges into the existing counter instead of starting a fresh 8. Unverified password addresses and unlinked accounts stay keyed by UID, and the browser never chooses the subject.

The site now requires an account. site-auth.js mounts a login gate on every visitor page (dashboard/editor, obfuscator, community scripts, key system, Creator Panel, staff, Get-Key, leaderboard, vault view) with email/password, Google, or Discord, and pages no longer start guest sessions; the admin and Discord panels keep their existing admin login. The public page (/obfuscation) needs no link and spends the signed-in account's balance through /api/obfuscation-tokens, which now rejects anonymous sessions. When the browser still holds a leftover anonymous Firebase session, signing in calls /api/claim-guest-vaults: the server verifies both ID tokens and moves every vault owned by the guest UID onto the signed-in account, so the vaults appear immediately in the editor and Creator Panel. Linking instead (email sign-up, Google, or Discord on the guest session) keeps the same UID, so no move is needed. The gate also offers a forgot-password view that sends a Firebase reset email, and it sets browserLocalPersistence before subscribing to auth state, so a deploy or browser restart keeps the user signed in. /obfuscate in Discord still issues a private link of the form https://voidedx.vercel.app/obfuscation?vx=<token> (with the /obfuscationvx=<token> rewrite) that uses the user's Discord balance; upload a .lua/.txt file or paste code in the command, or open the link and paste it there. Both paths expose strength, armor layers (1-6 or the strength default), junk preamble (off/normal/heavy), gibberish comments, messy or compact layout, tamper check, and extra string splitting, and the page can still save the generated copy to a new vault. The page was rebuilt with segmented controls and switches instead of native selects, a token card that draws one segment per daily credit, a live source readout (characters, lines, bytes), result stats (size, characters, lines, build time) plus a chip row of the settings used, remembered build choices with a Reset button, Paste/Clear source tools with a confirmation dialog, Ctrl/Cmd+Enter to build, and the English/Português do Brasil switcher from i18n.js.

New Firestore collections: obfuscationTokens/{subject} keeps the daily counter and bonus balance, where subject is discord:<userId> or web:<firebaseUid>; obfuscationTokenAliases/{sha256(email)} maps a verified email to its web ledger so sign-out/sign-in and provider switches share one allowance; obfuscationTokenGrants/{autoId} is the admin grant history. obfuscationSessions/{token} keeps the preloaded source, level, filename, and expiry, and obfuscationSessionOwners/{discordUserId} points to the user's current link. Link tokens are 24-byte base64url values and last 7 days; a user keeps one active link at a time, and running /obfuscate again refreshes its source and reuses the token. Spending and granting run in transactions, so a token cannot be double-spent and a bonus grant cannot be lost. The link stays bearer-style: anyone who has it can spend that user's remaining tokens until it expires. Vault saving uses the signed-in Firebase account and the same record shape as the Creator Panel, including the 5-vault limit and 10-hour auto-delete, and the vault is owned by that account. The claim route moves every vault whose uid still equals the verified guest UID; it does not merge tokens or community scripts.

Discord command registration is unchanged for names and options; only the /obfuscate description and the file/code help text changed, so the existing registered command still works and re-registering is optional.

The obfuscator page (and the editor) obfuscates in the browser with the same engine (lua-medium.js plus lua-voidedx-armor.js and the prometheus-engine assets) used by the Creator Panel, so those files must be deployed with the page.
